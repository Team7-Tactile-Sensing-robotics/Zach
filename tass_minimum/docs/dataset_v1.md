# Version 1 static-contact simulation dataset

This is synthetic data generated by Zach, not ruler measurements or readings
from a physical digital force gauge. It is intended to exercise a data/ML
pipeline before hardware collection. Simulation accuracy must not be reported
as real-world contact identification accuracy.

## Protocol and teacher feedback

The first draft resolves the inconsistent trial counts as **20 independent
simulated trials for each of 16 conditions = 320 trials**. This gives 80 trials
per location and 80 per force class. It does NOT simultaneously meet “100 trials
per location.” To require exactly 100 per location, use 25 per condition (400
total). To require 100 per location-force combination, use 100 (1600 total).
Change `trials_per_condition` explicitly rather than counting windows as trials.

| Item | Version 1 setting |
| --- | --- |
| Contact classes | 20%, 40%, 60%, 80% |
| Force classes | 1 N, 2 N, 5 N, 10 N |
| Conditions | Every location crossed with every force: 16 |
| Trial | One independently seeded static contact application |
| Recorded window | 1.000 s, after ideal static equilibrium is established |
| Sample rate | 48,000 samples/s |
| Classifier input | Four piezo voltage time series: 48,000 × 4 per trial |
| Excitation | Four 250-ms slots, ordered pair1, pair2, pair3, pair4 |
| Pulse | 1-ms smooth pulse, nominal peak 0.002 N, 10 ms after each slot starts |
| Labels | `location_class` and `force_class`, each an integer 0–3 |
| Split | 14 train, 3 validation, 3 test trials per condition |
| Total split sizes | 224 train / 48 validation / 48 test |

The response is continuous across the four slots: each slot includes the next
pulse and any residual vibration from earlier slots. A sample means the entire
1-second trial window, not one individual timestamp or four independent trials.
There is no extra artificial settling interval in the simulator: mechanical
initial conditions are computed at static equilibrium, and vibration begins at
rest. This is an idealization, not a simulation of the person's hand settling.

A proposal-ready clarification:

> We record synchronized four-channel piezo voltage time series at 48 kHz. Each
> trial yields one 1-second window after the applied force has stabilized, with
> four sequential 250-ms actuator slots. Each window has two categorical labels:
> contact position and static force magnitude. We will train separate location
> and force classifiers using temporal inputs (for example, a 1D CNN per task).
> A spectral-feature classifier provides a baseline. Data splits are by complete
> trial and, for hardware validation, by collection session/operator; overlapping
> windows from one trial must never appear in different splits.

No classifier is trained by the generator. The raw data supports a temporal
model; FFT/spectral features can also be computed on actuator-aligned slots.
Fit any normalization or feature selection only on the training set. Treat
synthetic splits as a development check, not evidence of hardware performance.

## Location definition: two incompatible descriptions in the proposal

The default `location_reference="total_tendon"` places contact at the specified
fraction of the **full vibrating route**, measured from its spool/feed endpoint.
It is not a fraction measured from the joint axis. The generator also records
signed path distance relative to the nearest route projection of the joint axis.
Thus negative distances are on the base side of that reference.

The optional `segment2_from_joint` mode instead places the mechanical contact
at 20/40/60/80% of segment 2 length from the joint. It projects that point onto
the routed tendon to obtain an acoustic clamp coordinate. This nearest-point
mapping is an explicit approximation, not a measured contact-transmission law.
These two modes represent different experiments; choose one before hardware
collection. Labels are fractions in the selected convention, stored in the protocol.

For the full-tendon draft, acoustic contact position and mechanical load lever
arm are independent: force acts at the configured 40-mm lever arm on segment 2.
This preserves the original full-string classes but is not a literal model of
a probe applying force at each corresponding world point. Some full-route
locations are on segment 1. The experiment's physical mapping must be resolved
before claiming this simulates a single probe pressing the actual marked point.

Contact is clamped to the nearest mesh node. The manifest preserves nominal,
jittered/requested, and grid-snapped positions. Do not present a finer spatial
accuracy than the configured mesh supports.

## Static force and model assumptions

The archived v1 dataset used the legacy torsional spring. New runs use the
configured shared spring model, including extension-spring geometry when enabled.
At a held joint angle q=0.5 rad, with perpendicular force at lever arm r, the
required tension is computed from:

```
arm = -dL/dq
T = (spring_resisting_torque(q) + F * r) / arm
winding = L0 + slack + T/k_tendon - L(q)
```

The pose is assumed held by an ideal motor controller adjusting winding. Static
velocity and acceleration vanish; force and tension are not interchangeable.
The equivalent winding is checked against physical tendon length. Force is
constant within each trial, with a random ±2% deviation from its class target.
`force_label_N` stores the target; `actual_force_N` stores the simulated truth.

The reference hard-clamp model by itself cannot distinguish force magnitudes
at a fixed tension. In this dataset, force affects vibration through the above
static tension relationship. This relationship must be calibrated and validated
before using it to interpret real force-gauge data.

The static solver uses the same finite-difference string stiffness, nodal masses,
damping and hard-contact constraints as `models/string.py`. It diagonalizes the
constant system and integrates zero-order-held input samples exactly. It was
checked against the existing RK4 implementation. This is not the empirical
frequency-response approximation in `models/modal_string.py`.

All four actuator columns and four sensor channels are saved. The current
P4/fixed-end assumption makes pair4's mechanical response zero (sensor noise
can still be nonzero). Contact can also isolate subspans without a usable
actuator. `constrained_actuators` records actuators at fixed/clamped nodes.
The generator does not silently move a pair away from the endpoint. Real piezo
reaction-force sensing or a measured anchor extension requires updated physics.

Trial variations are seeded and class-independent: ±0.5 mm contact position,
±3% sensor gain, ±3% excitation amplitude, and 10 µV Gaussian sensor noise.
These are illustrative assumptions, not calibrated noise statistics. Model
parameters other than those variations are shared across all trials, so this
first version does not establish robustness to new hardware or materials.

## Run and inspect

From `Zach/`, with the environment activated:

```bash
OPENBLAS_NUM_THREADS=1 OMP_NUM_THREADS=1 python -m tass.dataset \
  --config tass_minimum/config/default.json \
  --protocol tass_minimum/config/experiments/dataset_v1.json \
  --output outputs/dataset_v1
```

Use a new empty output directory for every generation. The generator refuses
to overwrite existing data. Output contains:

- `trials/trial_XXXX.npz`: time, four voltage traces, four force-drive traces,
  two class labels, nominal physical labels and per-trial metadata.
- `manifest.csv`: trial IDs, condition, split, labels, seeds, physical ground
  truth, mesh positions and SHA-256 checksums.
- `model_config.json` and `protocol.json`: exact inputs.
- `summary.json`: completion marker, counts, shapes, assumptions and splits.

```python
import csv
import numpy as np
from pathlib import Path

root = Path("outputs/dataset_v1")
with (root / "manifest.csv").open() as stream:
    rows = list(csv.DictReader(stream))
train_rows = [row for row in rows if row["split"] == "train"]
with np.load(root / train_rows[0]["file"], allow_pickle=False) as trial:
    X = trial["piezo_V"]              # (48000, 4); model input
    y_location = int(trial["location_class"])
    y_force = int(trial["force_class"])
```

Do not use actual force, tension, motor angle, contact coordinates, filenames,
condition IDs or target labels as classifier features. Ground-truth and acquisition
metadata are for annotation and quality checks. Retain complete trial groups if
creating shorter windows later.

## Hardware collection counterpart

1. Choose the location convention. Mark the four positions using a ruler and
   record each measured distance in millimetres relative to the joint axis.
   Also document tendon-path coordinates if they are used as labels.
2. Reapply and release the rigid probe for each trial; randomize the condition
   order. Keep finger pose, excitation and sensor acquisition settings recorded.
3. Use the digital force gauge to establish the applied normal force. A proposed
   acceptance gate is ±5% of target for at least 0.5 s before recording, maintained
   through the 1-s window. Validate this threshold experimentally.
4. If the gauge supports logged output, synchronize it with piezo timestamps and
   retain the force trace. Otherwise record before/after readings and explicitly
   note that within-window force stability is unverified; do not claim a measured
   force time series from a manually read display.
5. Record the four piezo channels for exactly one second using the stated drive
   sequence. Save target force and measured mean/spread separately when available;
   reject or flag trials that fail the stability gate instead of relabeling them.
6. Record operator/session IDs and hold out entire sessions for final validation.

The simulated dataset satisfies an explicit time-series format; the hardware
procedure still needs the actual gauge interface, synchronization and acoustic
boundary/contact mapping to be established.
